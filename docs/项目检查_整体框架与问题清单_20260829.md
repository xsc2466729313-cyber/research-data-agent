# 项目检查：整体框架、现存问题与前端不足

> 检查日期：2026-08-29  
> 检查方式：对照 `README_START_HERE.md`、`docs/00–08`、冻结配置与当前源码/前端页面，不以文档宣称代替实现。  
> 口径：只写已经在代码、配置或真实运行产物中确认的事实；公开基准成绩是能力层诊断，不是乳腺癌临床有效性，也不是正式 SDTI。

---

## 1. 结论先行

当前仓库已经具备一套可运行的端到端骨架：用户输入宽泛研究方向或具体科研问题后，系统可以检索真实论文、生成研究方案、调用公开数据库 Adapter、做字段标准化与患者/样本关联、走医学安全规则和质量门，再导出 CSV / Excel / 质量报告。生产主链是「千问规划 + 公开数据 Adapter + 确定性规则守门」，不是 Mock 演示页。

与此同时，项目仍处在「工程骨架完整、正式评测未闭环、前端产品化不足」的状态：

1. **乳腺癌 Gold Set 仍为空模板**，正式 Retrieval F1、Faithfulness、Traceability、Repair Accuracy 和 SDTI 全部是 `NOT_EVALUATED`。
2. **后端能力明显多于前端暴露**：Quality V2、Gold Set 审核、Schema/Entity Matcher、Planning RAG、评测看板等 API 已存在，用户页面基本用不上。
3. **前端是单文件双工作台**，规划页与高级数据工作台叠在同一 `index.html` 中；小屏会丢掉关键信息，阶段导航不可点击，历史研究无法真正恢复。
4. **模块版本并存**：`research_planning` / `v2`、Schema Matcher V2/V3、Entity Matcher V2/V3、BM25/BGE/hashing 同时存在，默认链路与评测最优方案并不完全一致。
5. **文档债重**：`docs/` 下已有 50+ 份阶段报告，信息互相覆盖，新人很难判断「当前主链到底是哪一条」。

本文件用于后续改版、答辩和排期，不替代冻结 Schema、医学规则和 SDTI 公式。

## 2. 项目定位与产品目标

### 2.1 一句话目标

构建面向**乳腺癌精准治疗与药物反应**的科研数据智能整合系统：把自然语言科研问题转成真实、结构化、可追溯的患者/样本级数据集，而不是生成长篇医学回答。

典型问题：

> HER2 阳性乳腺癌中 PIK3CA 突变是否与新辅助治疗响应有关？

### 2.2 必须证明的五件事

| 记忆点 | 指标 | 当前状态 |
|---|---|---|
| 找得准 | Retrieval Precision | 正式 Gold Set 未冻结，`NOT_EVALUATED` |
| 找得全 | Retrieval Recall | 同上；公开 BEIR 仅作检索层诊断 |
| 整得真 | Faithfulness | `NOT_EVALUATED` |
| 查得回 | Traceability | 工程上保留 `source_id` / `raw_field` / `raw_value`，正式指标未评 |
| 改得对 | Repair Accuracy | 格式型清洗有效，正式指标未评 |

综合可信指标为冻结的 `SDTI`，公式不得自行改写。

### 2.3 第一版明确不做的事

- 全医学领域泛化
- 医学影像 / WSI 诊断模型
- 自动写论文
- 把细胞系药敏直接解释为患者疗效
- 把 HER2 IHC、HER2 FISH、ERBB2 CNA 当成同一字段

## 3. 整体框架

### 3.1 三层流水线

```text
第一层  科研需求与数据发现
        问题理解 → 文献 Evidence → Research Contract → Source Plan

第二层  多源数据处理与融合
        Adapter 取数 → Canonical Schema → 患者/样本关联 → Evidence 绑定

第三层  质量闭环与科研输出
        质量门 / 医学规则 → 修复或人工 review → 数据集、字典、报告、导出
```

责任边界：

| 层 | 允许做 | 不允许做 |
|---|---|---|
| 模型层 | 解析问题、生成计划、选择工具 | 直接写入患者事实，绕过安全层 |
| 数据适配层 | 从官方公开接口取数并登记来源 | 用猜测补齐不存在的记录 |
| 标准化 / 关联层 | 字段映射、保留原始值、低置信度隔离 | 低置信度自动合并患者 |
| 安全与质量层 | HER2、response_domain、冲突、发布门控 | 用模型自评替代 Gold Set |
| 评测层 | 在固定脚本和数据上计算指标 | 读取 test qrels 调参或伪造成绩 |

### 3.2 运行时主链

```text
用户输入 Topic / 科研问题
        │
        ▼
Guided Planning Workspace（默认首页）
  POST /api/research/topics
  POST /api/research/topics/{id}/literature-scan
  GET  /api/research/topics/{id}/question-candidates
  POST /api/research/questions/{id}/select
  POST /api/research/contracts/{id}/source-plan
        │
        ▼  「开始生成数据集」
两轮闭环  POST /api/v2/agent/closed-loop
        │
        ├─ Qwen 结构化解析与 function calling（无密钥则确定性兜底）
        ├─ Source Broker 选队列，禁止无 crosswalk 的患者级 Join
        ├─ GDC / GEO / cBioPortal / AACT / CIViC Adapter
        ├─ Canonical Schema + raw_field/raw_value/source_id
        ├─ 患者-样本关联（低置信度 → unresolved/review）
        ├─ 独立 Safety Layer：AUTO / REVIEW / REJECT
        └─ 质量门 + 缺口诊断 → 第二轮补充检索
        │
        ▼
分析矩阵 + 字段字典 + Evidence + 质量报告
Excel / CSV / Parquet 导出
```

高级数据工作台仍走 `POST /api/agent/tasks` 或同一闭环接口，用于查看质量门、队列漏斗、工具调用和溯源图。阶段 00 Mock 接口仅保留给回归测试，不再是前端主链。

### 3.3 仓库模块地图

```text
frontend/                 单页应用：index.html + app.js + styles.css + nginx
backend/app/
  agent/                  千问客户端、任务编排、闭环、质量门、导出
  research_planning/      规划工作台实际调用的 Topic → Contract 链路（v1）
  research_planning_v2/   PICO/PECO Agent API，前端未接入
  literature/             Europe PMC 等 Literature Provider
  rag/                    Planning RAG / 切片 / hashing 或 BGE embedding
  source_broker/          DatasetCandidate、覆盖矩阵、JoinPolicy
  sources/                gdc, geo, cbioportal, aact, civic, discovery
  normalization/          基因、药物、生物标志物标准化
  integration/            Schema/Entity Matcher V2/V3、融合、冲突
  evidence/               字段级 Evidence
  governance/             独立 Safety Layer
  quality_v2/             错误检测 / 修复候选 / 审核 / Research Readiness
  repair/                 阶段 09 Repair 闭环
  goldset/                初标、复核、来源验证、review queue
  evaluation/             SDTI、公开基准、overview
  retrieval/              BM25 / dense / fusion / rerank
configs/                  冻结 schema、医学规则、质量规则、vnext
goldset/templates/        空 CSV 表头
evaluation/               真实运行报告与产物
```

### 3.4 数据源与安全边界

| 来源 | 用途 | 现状 |
|---|---|---|
| GDC / TCGA-BRCA | 临床与组学文件发现 | Adapter 已接；大型下载默认关闭或限量 |
| NCBI GEO | 表达与治疗响应队列 | 可解析如 GSE76360 Series Matrix |
| cBioPortal | 临床 + 组学队列 | 作为患者主表锚点，避免分子孤立记录 |
| AACT / ClinicalTrials.gov | 试验登记 | 已接 |
| CIViC | variant–drug–disease 证据 | 已接 |
| DepMap / PRISM / GDSC | 细胞系药敏 | 任务书中的增强项，不是当前主链 |

硬约束（实现必须遵守，不可被模型覆盖）：

- HER2 IHC 2+ 不得自动判为 Positive
- ERBB2 CNA amplification 不等同 HER2 IHC positive
- 低置信度患者/样本关联进入 unresolved/review
- 高权威来源不可解释冲突不得自动选边
- 细胞系 `AUC/IC50` 与患者 `pCR/response` 必须用 `response_domain` 区分
- 标准化必须保留 `raw_field`、`raw_value` 和真实 `source_id`

### 3.5 部署形态

| 入口 | 地址 |
|---|---|
| Docker 前端 | `http://127.0.0.1:8888/` |
| 后端 API | `http://127.0.0.1:8000` |
| Swagger | `http://127.0.0.1:8000/docs` |
| 健康检查 | `GET /health` |

- 前端镜像只有静态三件套：`index.html`、`app.js`、`styles.css`。
- 模型凭据走本机 `.env` 或内存会话（最长 2 小时），不写入任务结果。
- CORS 仅放行 localhost 若干端口；任务结果保存在进程内存字典中，重启即丢失。
- Docker 默认 `RAG_EMBEDDING_BACKEND=hashing`，与评测中表现更好的 BGE 不是同一默认。

### 3.6 前端信息架构

默认首页是 **Guided Research Planning Workspace**（三栏：阶段导航 / 向导 / 依据与方案）。  
点击「查看技术详情」后切换到 **高级数据工作台**（同一 HTML，靠 `body.is-advanced-workbench` 显隐）。

规划页五步：提出方向 → 查找依据 → 明确问题 → 制定方案 → 准备数据。  
完成后可「开始生成数据集」，不必先跳到旧页。

高级工作台保留：千问连接、研究问题表单、质量门、分析矩阵、字段字典、溯源图、闭环对比；研究方案/队列/身份对齐和检索审计放在折叠抽屉里。

## 4. 已经落地、可以据实展示的能力

这些能力在代码和测试中存在，可以演示，但不要把它们说成正式 SDTI。

1. **规划工作台**：Topic → 真实论文扫描 → 候选问题 → Research Blueprint → Source Plan。
2. **真实 Adapter**：GDC、GEO、cBioPortal、AACT、CIViC 均有独立测试；前端不再走 Mock。
3. **可追溯标准化**：Canonical Schema 冻结；原始字段/值保留；禁止无 crosswalk 的跨队列患者拼接。
4. **医学安全门**：HER2 / 身份 / response_domain / 高权威冲突有确定性规则。
5. **两轮闭环**：第一轮保存完整结果，第二轮按缺口补充检索并对比 coverage、target match、traceability。该 progress score 只作任务内反馈。
6. **导出**：CSV、Parquet、含多工作表的 Excel、质量报告。
7. **公开能力层评测**（诊断用，不是临床成绩）：
   - Valentine 字段对齐 V2 宏平均 F1 `0.8451`（V3 为 `0.7994`，故生产仍用 V2）
   - DeepMatcher 实体匹配 V2 宏平均 F1 `0.7408`（V3 为 `0.5579`，故生产仍用 V2）
   - BEIR 五组：BGE-small-en-v1.5 nDCG@10 `0.3880`，tuned BM25 `0.3147`
   - 清洗：格式型任务高，Hospital/Rayyan 缺失与语义错误为 `0.0000`
8. **测试规模**：`backend/tests/` 下约 70+ 测试文件，覆盖 Adapter、规划、闭环、评测门控和医学规则。前端几乎没有自动化测试。

## 5. 系统层问题与缺点

### 5.1 正式评测尚未闭环（最高优先级缺口）

- `goldset/templates/*.csv` 只有表头；`goldset/breast_cancer/` 只是工作区说明，不是冻结真值。
- 因此正式 SDTI、Research-Ready Rate、专家认可率都不得对外发布。
- 端到端对照矩阵脚本会把 Rule / Qwen / Single-source / Multi-source / Full Agent 标为 `NOT_EVALUATED`，直到冻结 Evaluation Contract 和人工 Gold Set 就绪。
- 公开基准（BEIR、Valentine、DeepMatcher、Raha/HoloClean、EBM-NLP）不能外推为乳腺癌队列效果。

### 5.2 规划与问题理解仍然偏模板

前端规划主链调用的是 **Phase 1** `/api/research/*`，不是已经实现的 **Phase C** `/api/v2/research/plan`。

`ResearchFormulationAgent` 对「乳腺癌 + 新辅助」直接返回固定三道候选题（PIK3CA–pCR、受体亚型–pCR、基因表达预测 pCR）。宽泛主题走通用 fallback，novelty / data availability 是启发式分数，不是系统综述或真实取数验证。

无论文 Evidence 时，v2 规划会标记 `GENERIC_FALLBACK`，这是正确的诚实行为，但也说明「从文献自主发现问题」尚未成为默认产品路径。

EBM-NLP 问题解析宏平均 F1 约 `0.4900`，Interventions 更弱。当前方法主要是词典和局部上下文，没有序列标注模型。

### 5.3 检索默认与评测最优不一致

| 位置 | 实际默认 | 评测更优 |
|---|---|---|
| `configs/vnext.yaml` 主检索 | BM25 | BGE nDCG@10 更高 |
| Docker RAG embedding | `hashing` | 真实 BGE |
| 查询理解生产模式 | `compat` | A–E 消融未证明可全局替换 |

hashing embedding 只能做离线回归，不能当成语义检索能力。中文问题检索英文论文、医学缩写和跨语言同义表达还没有单独统计。

闭环实测样本很小：公开报告里真实 Qwen 两轮对照只有 1 个任务；中间智能体替换是 3 题 × 3 次。不足以形成模型排名。

### 5.4 数据整合能力不均衡

- **字段对齐**：公开表任务整体较好，但缩写、布尔列、低重复值列仍不稳；尚无乳腺癌 canonical schema 字段 Gold Set，AUTO/REVIEW/REJECT 阈值 `0.90/0.65` 未用医学验证集校准。
- **实体匹配**：商品实体任务波动大（Walmart-Amazon F1 `0.4939`）；不能外推到患者身份。缺少 False Merge Rate 的医学 Gold Set。
- **清洗 / 修复**：大小写、单位、数字格式容易做；缺失值、日期语义、医学语义几乎做不了。Quality V2 已把检测、候选、安全应用和 Readiness 拆开，但前端没有审核工作台。
- **多源融合**：无 crosswalk 时禁止患者级 Join 是正确的，代价是很多「看起来相关」的队列无法拼成一张分析表。METABRIC 有 PIK3CA、GSE76360 有响应、二者不能贴到同一患者——系统会停，用户可能误以为失败。

### 5.5 后端能力未接到产品面

下列模块有 API 和测试，用户页面基本不可见、不可操作：

| 能力 | 接口/模块 | 前端状态 |
|---|---|---|
| Research Planning V2 | `POST /api/v2/research/plan` | 未用 |
| Quality V2 检测/候选/审核 | `/api/v2/quality/*` | 未用 |
| Schema / Entity Matcher | `/api/v2/schema/match*` `/api/v2/entity/match*` | 未用 |
| Safety 独立裁决 | `POST /api/v2/governance/decide` | 未作为独立操作面 |
| Gold Set 初标与 review queue | `/api/goldset/*` | 无策展 UI |
| 评测概览与产物 | `/api/evaluation/*` | 页面 HTML 已移除，JS 仍残留渲染函数 |
| Planning RAG / 科学图谱 | `/api/rag*` 一类接口 | 无独立页面 |
| 阶段 00 Mock | `/api/tasks/mock` | 仅测试 |

结果是：答辩可以讲很多「已实现模块」，演示时用户只能走规划向导 + 生成数据集这一条窄路径。

### 5.6 运行时工程限制

- 任务结果、千问会话、规划中间态都在**进程内存**里，重启、多 worker、容器重建后全部丢失。
- 没有用户账号、权限、任务历史库；「当前研究」只存在于当前页的 JS 状态。
- Adapter 大型下载默认关闭或限量，真实队列规模受 `max_sources` / `max_records` 和缓存约束。
- 外部 API 字段可能变化，需要靠 source manifest 和哈希复核，系统没有持续监控。
- CORS 与绑定地址面向本机演示，不是多用户生产部署形态。
- 依赖千问密钥；未配置时走确定性兜底，页面若仍显示「千问驱动」会造成误解。

### 5.7 版本并存与默认选择债务

生产默认已经根据公开基准退回更强的 V2 Matcher 和（配置上的）BM25，这是正确的，但代码里仍保留：

- SchemaMatcherV3 / EntityMatcherV3 及 v2plus
- hashing dense fallback
- research_planning 与 research_planning_v2 两套合同 模型
- MockPipeline
- 评测看板残留 CSS/JS

新人容易把「仓库里有 V3」理解成「线上在用 V3」。需要一份更短的「当前默认主链」说明，而不是继续追加阶段文档。

### 5.8 数据覆盖相对任务书仍有缺口

任务书第一版还列出 DepMap / PRISM / GDSC 细胞系药敏为增强项；完整知识图谱、自动论文写作明确不做。当前 KG 只是 Planning RAG 的 MVP，不是可用的领域图谱产品。固定测试队列（TCGA-BRCA、METABRIC、SCAN-B、GSE25066、GSE76360 等）并非每次任务都会真正取全，而是按问题与预算选择。

## 6. 前端页面专项不足

检查对象：`frontend/index.html`（约 495 行）、`frontend/app.js`（约 2890 行）、`frontend/styles.css`（约 1290 行）。无组件库、无路由、无前端测试、无视觉回归。

### 6.1 双工作台叠在同一页，心智负担重

- 规划工作台与高级数据工作台共用一个 HTML。默认用 CSS 隐藏后者；切换只靠 `body` class。
- 两套品牌并存：规划侧是 `SDA / 科研数据助手`，高级侧是 `BRCA / 乳腺癌科研数据智能体`。
- 规划完成后生成数据集，结果写进隐藏的高级工作台；用户若不到「查看完整质量与溯源结果」，会以为只有一行成功摘要。
- 高级工作台仍暴露大量技术旋钮：执行模式、检索入口上限、单表记录上限、缺口补全轮次、是否启用模型、是否允许兜底、是否闭环。对「只有一个研究方向」的目标用户过载。
- 标题、页脚、配置面板反复强调「千问」，但实际可能 `used_qwen=false`。缺少「本次是否真正调用了模型」的首屏强提示。

### 6.2 规划向导交互不完整

| 问题 | 证据 |
|---|---|
| 左侧 01–05 阶段按钮不可点击 | `data-planner-stage` 只被用来改样式，没有 click handler |
| 「当前研究」列表被 CSS 藏掉 | `.planner-recent { display: none }` |
| 即使显示也恢复不了历史 | 渲染了 `data-planner-recent`，但没有对应监听；状态不在 localStorage |
| 新建研究会丢掉进行中的结果 | `resetPlannerWorkspace()` 清空内存状态，无确认框 |
| 规划一次性跑完五步 | 用户无法在文献扫描后停下来自己选论文，也无法跳过某步 |
| 候选问题默认折叠 | 系统自动采用第一项；用户不容易比较可行性分数和 Evidence 条数 |
| 右侧空态说明被隐藏 | `.planner-empty p { display: none }`，首次进入几乎看不到引导文案 |
| 中英混杂 | 空态仍写 `Research Blueprint`、`Source Plan`、`Required/Recommended/Optional`、`Full text/Abstract` |

规划成功后的中间栏信息密度偏低：一张 PICO 卡片 + 生成按钮。字段覆盖、Join Policy、论文列表都挤在右侧，而平板宽度下右侧整栏会被 `display: none`。

### 6.3 响应式与信息丢失（前端最严重的产品缺陷之一）

| 断点 | 行为 | 后果 |
|---|---|---|
| ≤1180px | 三栏变窄 | 尚可用 |
| ≤980px | **右侧「研究依据 / 方案 / 数据准备」整栏消失** | 规划的核心证据用户看不见 |
| ≤760px | **左侧阶段导航整栏消失** | 无法感知当前走到哪一步 |
| ≤1120px（高级页） | 顶栏导航直接 `nav { display: none }` | 质量门、矩阵、溯源锚点丢失 |

也就是说：在常见笔记本分屏和几乎所有手机宽度上，规划页只剩中间输入区，依据和方案都没有入口。这与「三栏工作台」设计文档不符。

另外，后期覆盖样式把 `.planner-recent`、阶段 `small` 文案再次隐藏，和更早的 680px 规则叠在一起，媒体查询重复、互相覆盖，后续改样式很容易改一处坏另一处。

### 6.4 高级工作台：内容全，但不是研究者界面

优点：质量门、分析矩阵、中文字段字典、结局分布、溯源点线图、闭环对比、导出按钮都在。

不足：

1. **首屏不是数据，而是配置。** 进入技术详情先看到「连接千问 API」、模型名、长表单，而不是已经生成的矩阵。
2. **研究方案、队列漏斗、身份对齐被折进 `<details>`。** 这些其实是科研用户最该看的内容，却被标成「方法抽屉」。
3. **检索审计、工具调用、候选登记同样折叠。** 失败时用户很难在当前页定位是哪个 Adapter 出错。
4. **错误态偏技术。** 规划失败、Provider 未配置、质量门 REVIEW/REJECT、文献为空、字段不足，多数只是红字或 toast，没有统一的「发生了什么 / 为什么 / 下一步」模板。
5. **AUTO / REVIEW / REJECT / 模型建议** 四种来源在界面上没有始终如一的视觉语言。文档自己也承认用户分不清「模型建议、算法结果、规则阻断、人工待审核」。
6. **表格。** 宽表靠横向滚动；关键字段/全部字段切换有，但缺少列冻结、搜索、按来源过滤、缺失高亮、点击单元格看 Evidence 的稳定交互。验收文档要求「点击字段查看 Evidence」，当前更多是溯源图 + 原始特征对话框，不是单元格级证据抽屉。
7. **评测残留。** `app.js` 仍有 `renderSystemEvaluationDashboard`、`renderUnifiedEvaluation` 等，对应 DOM 已从 `index.html` 删除；`nginx.conf` 把 `model-evaluation.html` 直接 404。死代码增加维护成本，也容易让人以为前端还有评测页。
8. **无任务列表。** 不能打开历史 task_id，不能对比两次运行，刷新即丢失（后端也是内存字典）。
9. **无人工审核队列 UI。** 高风险修复、低置信度匹配、Gold Set 分歧都只能走 API。
10. **无登录、无权限、无协作批注。** 作为科研工作台，无法把 REVIEW 项交给另一位审核人。

### 6.5 可访问性与一致性

- 有 skip-link、部分 `aria-live`，规划 Tab 有 `role="tablist"`，整体可用。
- 阶段按钮对键盘用户表现为可聚焦，但按下无导航，属于误导性控件。
- 进度条是估算百分比（10/38/64/82/96），与真实后端阶段并非严格对应；长时间 Adapter 请求只有「请勿关闭本页」。
- 没有取消正在进行的规划或闭环任务的按钮。
- Toast 2.6 秒消失，失败原因如果只靠 toast 会看漏。
- 中文展示依赖前端硬编码词典（药物名、阳阴性、术式等）。未收录的值保持英文或原始代码，同一表格里中英混排。
- 配置面板写「凭据落盘 否」，同时支持 CSV 导入 Key；安全说明较完整，但普通用户仍可能把 API Key 粘进对话记录。

### 6.6 前端工程缺陷

- 单文件 2800+ 行 JS：规划、Agent 结果渲染、评测残留、溯源图、千问会话全挤在一起，无法按路由拆包。
- 无 TypeScript、无组件边界、无前端单测；验收只写了 `node --check frontend/app.js`。
- 无 E2E / 视觉回归，文档已承认这一点。
- 静态资源用 querystring 版本号（`?v=20260829-user-ui-3`），Docker 构建后仍需靠 `Cache-Control: no-store` 避免旧页；历史上发生过克隆 `main` 看到旧页面的问题。
- 前端为了兼容多端口会探测 `8000/8001/8002`，并发送探测用 POST；本机同时开多个旧容器时，可能钉到错误后端。
- 没有 loading skeleton；长表格一次性 innerHTML 渲染，大数据量会卡。
- 没有暗色模式需求，但印刷/答辩投影时蓝底白字对比一般，图表全是 CSS 条，没有真正的可导出统计图。

### 6.7 对照任务书的前端缺口

任务书要求的「高级筛选、错误修复确认、前端证据查看、质量报告 HTML」只部分落地：

- 高级筛选只存在于技术页表单，规划页没有。
- 修复确认没有人机审核界面。
- Evidence 以溯源图和来源表为主，不是字段级点击即见。
- 质量报告可下载 JSON/导出，页面内没有独立、可打印的 HTML 报告视图。
- Docker 一键启动和页面可打开已经满足；「看起来像完整科研工作台」仍差一截。

## 7. 文档与协作问题

`docs/` 内已有五十余份 Markdown，包括阶段 00–10、Phase 1–F、VNext A/B、多份「最终报告」。对维护的影响：

- 「当前主链」分散在 `README_START_HERE.md`、`QWEN_RESEARCH_AGENT.md`、`FRONTEND_PLANNING_WORKSPACE.md`、`FINAL_INTEGRATED_REPORT_20260829.md` 中，结论不完全同一时刻。
- 前端文档仍写访问 `127.0.0.1:8888`，功能报告又写 `127.0.0.1:8000/`，本地 uvicorn 与 Docker 入口容易搞混。
- 冻结规则是清楚的（Schema、医学规则、SDTI 公式），但「哪些 API 是生产默认、哪些只是评测入口」缺少一张活的表。

建议后续只维护三份活文档：本检查清单、`README_START_HERE.md`（怎么跑）、评测报告（成绩与边界）。其余阶段文档改为归档，避免再写第三份「最终」。

## 8. 问题优先级（建议）

### P0：演示与诚实性

1. 首屏明确本次是否调用了千问、是否兜底、Gold Set / SDTI 仍为未评测。
2. 规划失败、文献为空、质量门 REVIEW/REJECT、Adapter 失败用同一套错误模板。
3. 小屏至少保留「依据 / 方案 / 数据」入口，不要把右栏直接 `display: none`。

### P1：规划页变成真正的向导

1. 阶段导航可回看已完成步骤。
2. 历史研究可恢复（至少 localStorage + task_id）。
3. 候选问题、论文 Evidence、Join Policy 在中间栏可见，而不是只在可能被隐藏的右栏。
4. 去掉或翻译残留英文产品词。

### P2：把已有后端接到人能用的面上

1. 人工 review queue（身份、HER2、高风险修复）。
2. 字段点击查看 Evidence。
3. 任务历史与导出归档（不要只靠内存）。
4. 决定是否让前端改走 `/api/v2/research/plan`，避免两套规划逻辑长期分叉。

### P3：评测与默认对齐

1. 建设 20–50 题乳腺癌 Gold Set（development / validation / frozen_test）。
2. 生产检索默认是否切到已评测的 BGE，单独做一次延迟/成本验收。
3. 清洗拆成 Detection / Repair / Review 三个可独立报告的指标。
4. 删除或隔离评测残留前端代码和未默认启用的 V3 入口说明。

### P4：工程收敛

1. 拆分 `app.js`，去掉死代码。
2. 补最小 E2E：Topic → 规划 →（允许失败的）生成数据集 → 错误态。
3. 任务结果持久化。
4. 文档减枝，只留当前主链。

## 9. 不能据此声称的事项

- 不能把 BEIR / Valentine / DeepMatcher 分数写成乳腺癌临床效果。
- 不能把未调用千问时的兜底成绩写成 Qwen 成绩。
- 不能因为字段匹配高分就放宽患者合并。
- 不能把「11/11 阶段已完成」理解成产品已经评测完成或可以临床使用。
- 不能把第二轮闭环 progress score 或 target match 当作 SDTI。

## 10. 一页对照表

| 维度 | 现在 | 主要缺口 |
|---|---|---|
| 产品形态 | 本机科研数据 Agent，规划页 + 技术页 | 不像可持续使用的研究工作台 |

| 前端 | 单页三栏向导，能跑通主路径 | 小屏丢栏、阶段不可点、无历史、无审核、死代码 |
| 工程 | 后端测试多，Docker 可起 | 前端无测试；文档过多；结果不持久 |
