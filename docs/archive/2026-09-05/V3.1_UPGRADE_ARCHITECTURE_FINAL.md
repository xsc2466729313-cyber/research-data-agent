# 0. 对 V3.0 的审查结论

## 0.1 V3.0 必须保留

V3.0 的骨架正确，V3.1 全部继承：

- 新智能在上，旧治理在下，编译层在中间
- `/api/v30/*` 作为新编排入口，`/api/v3/research/*` 与 `/api/agent/tasks` 保留
- Router、Scientific Planner、Data Discovery、Multimodal Extraction、Evidence Graph 五个旁路模块继续存在
- 肿瘤任务编译回 Frozen Research Contract，执行仍走 `ResearchAgentService`
- 不修改 `canonical_schema.yaml`、`medical_rules.yaml`、SDTI 公式
- 新模块不得写 CanonicalRecord，不得生成患者行
- 证据图禁止跨研究患者边
- 无文本层 PDF、低置信度读数不得进主表

## 0.2 V3.0 仍不像 ChatGPT 类科研 Agent 的原因

| 缺口 | 表现 | V3.1 补法 |
|---|---|---|
| 交互是流水线 | 用户一提交就进 Planner / 取数 | 增加 Research Copilot |
| 发现仍偏医学种子 | Discovery 第一批工具几乎都是肿瘤库 | 增加 Universal Source Registry |
| Schema 只有冻结肿瘤包 | 通用问题没有合法目标字段集 | 增加 Schema Generator，产出任务级 schema_pack |
| 几乎没有研究记忆 | 只有千问凭据会话，约束不能跨轮累积 | 增加 Research Session Memory |
| 图像能力不可展示 | V3.0 为防猜数直接标未实现 | 增加 Figure Understanding Demo，只理解不入库 |
| 优先级偏后台 | P0 先做桥接和兼容，用户感知来得晚 | P0 改为 Copilot + Router + Planner |

V3.1 不是把系统改成自由浏览 Agent。它只是让用户先经历“理解—建议—澄清”，再进入 V3.0 已经设计好的可信流水线。

# 1. 最终系统定位

## 一句话定位

**这是一个通用科研数据发现与可信整合智能体：先以对话理解研究目标，再发现和解析多源数据，最后用可替换的领域插件做可信收口；医学是第一个高质量领域插件，不是系统本体。**

## 它不是什么

- 不是医学数据系统
- 不是临床决策系统
- 不是可以随便生成表格数字的 ChatGPT
- 不是推倒 Adapter / Schema / Quality 后的新框架

## 它是什么

- 上层：通用科研交互、规划、发现、抽取、记忆、证据图
- 下层：可信数据工厂（来源、原始值、对齐、质量门、评测）
- 插件：医学规则包 + 冻结 Canonical Schema + 官方肿瘤 Adapter

医学继续作为最佳实践案例和回归安全网。通用科研能力走上层与注册表，不写进医学内核。

# 3. Research Copilot 交互层

## 3.1 为什么放在 Planner 之前

V3.0 的 Router 只能分流，Planner 会立刻生成合同。用户因此感觉“提交后系统自己跑完一套固定流程”。Copilot 把“研究对话”从“合同编译”里拆出来：先对齐目标，再允许进入 Planner。

Copilot 不替代 Router，也不替代 Planner。

```text
所有用户消息
    → Router          先判断是不是科研
         ├─ CHAT / CONCEPT_QA     → Copilot 只作简短回答，不建合同
         └─ RESEARCH_*            → Copilot 理解 / 建议 / 澄清
                                      └─ 用户确认足够后 → Planner
```

## 3.2 输入

| 字段 | 含义 |
|---|---|
| session_id | 研究会话，必须 |
| message | 本轮用户原话 |
| attachments | 可选文件清单 |
| memory_snapshot | 本会话已确认目标、约束、排除来源 |
| route | Router 的判定，Copilot 不得自行改成 INTEGRATE |

## 3.3 输出

| 字段 | 含义 |
|---|---|
| understood_goal | 研究对象、目标、粒度的复述 |
| suggested_data_needs | 可能需要的数据类型，标明“建议而非已找到” |
| clarifying_questions | 最多 1 到 3 个必要问题 |
| ready_for_planner | 是否已具备进入 Planner 的最小信息 |
| user_visible_reply | 给用户看的一段结构化回复 |
| memory_patches | 本轮要写入 Session Memory 的增量 |
| blocked_reason | 若是闲聊或概念问答，说明为何不进入科研链 |

`ready_for_planner=false` 时，禁止调用 `/api/v30/plan` 的自动冻结，更禁止 `/integrate`。

## 3.4 标准回复结构

用户说：“我想研究 HER2 阳性乳腺癌耐药机制”

Copilot 应先回复，而不是开跑：

```text
理解
  研究对象：HER2 阳性乳腺癌
  目标：耐药机制分析
  当前粒度：尚未确认（患者队列 / 细胞系 / 知识证据）

可能需要（建议，尚未检索）
  - 临床治疗与响应
  - 基因表达
  - 突变信息
  - 药物响应
  - 明确的 response_domain，避免细胞系药敏冒充患者疗效

需要你确认的问题
  你的研究重点是机制探索，还是疗效预测？
```

用户回答后，Copilot 再决定是否进入 Planner。若用户说“疗效预测，只要公开新辅助队列”，记忆层记下偏好，Planner 才能把结局域和来源约束写进合同。

## 3.5 与 Router / Planner 的关系

| 角色 | 负责 | 不负责 |
|---|---|---|
| Router | 是不是科研、哪个领域、能不能进 Copilot | 写合同、提问措辞、取数 |
| Research Copilot | 研究对话、数据需求建议、必要澄清、回述结果 | 冻结合同、选 Adapter、改质量门 |
| Scientific Planner | 把已澄清内容编译成 General Contract | 和用户来回聊天 |

Router 仍是第一闸门。Copilot 看到 `CHAT` 或 `CONCEPT_QA` 时，只回答概念，并明确“这还不是数据任务”。只有 Router 给出 `CLARIFY` / `PLAN` / 后续研究路由时，Copilot 才进入科研对话模式。

## 3.6 是否需要 Session 状态

需要。没有会话状态，Copilot 无法做到第二轮“不要 METABRIC”、第三轮“加入 PIK3CA”。会话状态不放在 Copilot 自己的隐式上下文里，而放在 Research Session Memory，便于隔离、过期和审计。

Copilot 每轮只读本会话记忆，并提交增量补丁。它不保存千问密钥，不保存其他研究的对话。

## 3.7 如何避免普通聊天进入科研流程

采用三道闸，而不是一道：

1. **Router 闸：** 无研究对象、无数据/验证意图，判定 `CHAT` 或 `CONCEPT_QA`。
2. **Copilot 闸：** 即使话里出现“癌”“星”“材料”，若只是名词解释，`ready_for_planner=false`，并拒绝写入“已确认研究目标”。
3. **Planner 闸：** 没有 Copilot 的 ready 标记，或没有用户对关键澄清的回答，不得冻结合同。

示例：

- “你好” → Router=CHAT → Copilot 简短引导，不进入 Planner
- “什么是 HER2” → Router=CONCEPT_QA → 解释概念，不问数据源
- “我想研究 HER2 阳性乳腺癌耐药” → Router=CLARIFY → Copilot 复述并提问
- “开始找数据”但尚无确认重点 → Copilot 继续问，不调用 Discovery

前端现有本地闲聊规则降为无模型时的回退，不再单独决定是否开跑完整协议。

# 4. Universal Source Registry

## 4.1 目标

让 Discovery 不再把医学种子目录当作世界本身。Registry 是**领域来源插件目录**：医学、天文、材料各自注册能力，Discovery 只按合同领域和模态查询，不在服务代码里写死“先搜 TCGA”。

现有肿瘤 Adapter 不重写。它们作为医学插件的 `fetch_binding` 被登记进去。

## 4.2 注册方式

来源不靠在 Discovery 里增加分支来“支持新领域”，而靠登记一条注册项。

登记通道：

1. 配置登记：`configs/v30/source_registry/` 下按领域拆文件
2. 运行时只读加载，启动时校验必填元数据
3. 医学已有 Adapter 的条目必须指向现有工具名，不得登记一套平行实现
4. 尚无 Adapter 的通用来源只能登记为 `discovery_only` 或 `catalog_only`
5. 未登记来源可以被论文链接临时提出，但 `verification_status` 只能是 unverified，且不得自动 fetch

禁止：在 `ResearchAgentService`、GoalLoop 或 Discovery 服务里继续堆领域 if-else 库名。

## 4.3 数据源元数据格式

每个注册项是一份来源描述，不是数据集实例。

| 字段 | 含义 | 约束 |
|---|---|---|
| source_key | 稳定键，如 `geo`、`nasa_mast`、`materials_project` | 全局唯一 |
| display_name | 展示名 | 给人看 |
| domains | oncology / astronomy / materials / general | 可多值 |
| resource_kind | official_api / repository / catalog / literature | 决定下一步动作 |
| locator_types | GSE / project_id / DOI / dataset_doi 等 | 发现结果必须匹配 |
| modalities | clinical_table / expression / spectrum / light_curve / structure 等 | 供 Planner 匹配数据需求 |
| access | public / token / not_implemented | token 不写入仓库 |
| fetch_binding | 现有工具名或空 | 有绑定才能被 ExecutionBridge 调用 |
| discovery_binding | 目录检索入口或空 | 只发现不取数 |
| field_hypothesis_hints | 可能覆盖的字段角色 | 只是假说 |
| join_policy | forbid_cross_entity / study_namespace_only / file_only | 医学患者跨库默认 forbid |
| status | active / seed / planned | planned 不得出现在自动 INTEGRATE |
| evidence_home | 官方门户 | 必须可回查 |

示例登记（设计清单，不是实现）：

医学插件（active，多数已有 Adapter）：

- TCGA / GDC
- GEO
- cBioPortal
- ClinicalTrials.gov / AACT
- CIViC
- PubMed / Europe PMC
- DepMap（必须带 preclinical 域）

天文插件（第一期多为 catalog / planned）：

- NASA 相关开放目录
- Zenodo
- ADS
- Open Supernova Catalog

材料插件（第一期多为 catalog / planned）：

- Materials Project
- PubChem

`planned` 来源可以出现在 Copilot 的“可能需要去哪里找”建议里，但不能被自动说成已经取到。

## 4.4 Discovery Agent 如何调用

```text
Planner 给出 domain + 数据模态 + 字段缺口
    → Discovery 查询 Registry：domains 匹配且 status≠disabled
    → 先收集 discovery_binding 可执行的目录结果
    → 每条候选带 source_key、locator、field_hypotheses、verification_status
    → SourceBroker 仍做覆盖组合
    → 仅 fetch_binding 指向现有 Adapter 的候选，才能进入 ExecutionBridge
```

天文或材料任务若只有 catalog 条目：Discovery 可以返回 Zenodo/ADS 候选和论文补充材料，然后交给 Extraction 解析用户提供或已下载的文件。没有 Adapter 就没有患者级或观测级官方 API 主表，Copilot 必须如实说明。

## 4.5 如何避免硬编码

1. 领域列表来自 Registry，不来自 Discovery 函数名。
2. 医学示范队列（GSE25066 等）继续留在旧执行引擎的肿瘤 fallback，不升格为通用注册真理。
3. 新增来源只加注册项；若要真取数，再单独立项写 Adapter，不在 Copilot 里临时代取。
4. Schema Generator 只引用 `source_key` 与模态，不写死库名到合同里。
5. 测试应断言：关闭医学插件后，肿瘤 INTEGRATE 不会静默改走天文目录冒充成功。

# 5. Dynamic Schema Pack Generator

## 5.1 位置

```text
Scientific Planner
      ↓  已澄清的对象 / 暴露 / 结局 / 模态
Schema Generator
      ↓  schema_pack（任务级）
Data Fusion / SchemaMatcher
      ↓  映射到 pack 字段，保留 raw_field / raw_value
Quality
      ├─ 医学高风险：冻结 medical_rules
      └─ 通用任务：仅溯源与置信度规则
```

它属于 Planner 的下游，不属于 Adapter，也不属于 Quality。

## 5.2 作用

现有医学 Canonical Schema 仍然是最强、最不可改的目标契约。通用科研不能把所有问题都塞进 `patient_id / HER2 / treatment / response`。Generator 为**当前任务**生成一份 schema_pack，供 SchemaMatcher 当作目标字段集。

它生成的是字段契约，不是数据行。

## 5.3 两类 pack

### A. 冻结医学 pack（强制）

当 Router/Copilot 判定 `domain=oncology`，并且出现患者/样本级临床或分子结局时：

- `schema_pack_id = oncology_canonical_v0.1`
- 直接绑定现有 `canonical_schema.yaml`
- Generator **不得改写、删减或替换** HER2、response_domain、patient/sample、source_id、raw 字段
- 可以在 pack 的 `extensions` 里增加本题非高风险辅助字段，例如用户明确要的某个协变量别名；辅助字段仍要 raw 保留
- 高风险字段的允许值、规则动作仍只来自 `medical_rules.yaml`

乳腺癌任务级目标仍应落在冻结字段上，例如：

- patient_id
- her2_status / her2_assay / her2_raw_value
- treatment
- response / response_domain
- source_id / raw_field / raw_value

### B. 任务级通用 pack（生成）

当领域不是医学患者主表，或用户明确只要文件/观测表时：

- Generator 产出 `schema_pack_id = task-{session 或 contract 短号}`
- 状态先为 `DRAFT`，进入融合前须 `READY` 或 `REVIEW`
- 必须包含溯源三件套：source_id、raw_field、raw_value
- 必须声明实体键，例如 `sn_id`、`sample_id`、`record_id`
- 不得借用医学高风险字段名来装非医学含义

Ia 型超新星示例字段：

- sn_id
- observation_time
- band
- flux
- redshift
- source_id
- raw_field
- raw_value

## 5.4 与现有 SchemaMatcher 兼容

V3.1 不重构 Matcher。兼容方式是让 schema_pack 提供 Matcher 已经认识的目标描述：

| pack 提供给 Matcher 的信息 | 用途 |
|---|---|
| 目标字段名 | 作为对齐目标，而不是只对齐冻结肿瘤字段 |
| 类型与允许值 | 供值画像和拒绝非法枚举 |
| 别名 / 角色 | 给通用表头做候选 |
| 风险级别 | high 则 AUTO 匹配后仍要规则复核 |

医学任务：Matcher 的目标集合 = 冻结 Canonical 字段。  
通用任务：Matcher 的目标集合 = 本任务 pack 字段。  
算法仍是现有 SchemaMatcher；换的是目标清单，不是匹配器实现。

融合层继续只输出带 raw 的映射记录。Generator 看不到、也不能改匹配后的值。

## 5.5 明确禁止

1. 不修改 `canonical_schema.yaml`
2. 不把生成 pack 存成新的冻结医学真理
3. 不因通用 pack 关闭医学质量门
4. 不把 HER2 IHC 2+、ERBB2 CNA、response_domain 放到可生成可覆盖的位置
5. 无用户确认、无对象/结局时，不自动生成看起来很完整的 schema

# 6. Research Session Memory

## 6.1 目标

支持连续科研交互，而不是每轮从零开始的协议重跑。

示例应能成立：

1. 第一轮：研究 HER2 耐药
2. 第二轮：不考虑 METABRIC，换公开新辅助治疗队列
3. 第三轮：加入 PIK3CA 因素

系统此时应知道：研究目标、已建议或已选来源、用户偏好、失败检索、已确认约束。

## 6.2 保存什么

只保存**研究过程状态**，不保存**事实表副本**。

| 记忆桶 | 内容 | 权威性 |
|---|---|---|
| goal | 对象、目标、重点（机制 / 预测等） | 用户确认后才算确认 |
| constraints | 只要公开数据、只要新辅助、不要细胞系 | 用户原话 + 规范化 |
| source_preferences | 排除 METABRIC、优先 GEO 响应队列 | 不得自动升格为已覆盖 |
| failed_searches | 工具、locator、失败类型、时间 | 供闭环避免空转 |
| confirmed_answers | Copilot 澄清题的回答 | 进入 Planner 的依据 |
| artifacts | contract_id、schema_pack_id、graph_id、task_id | 只存 ID |
| copilot_turns | 最近若干轮理解摘要 | 可过期压缩 |

明确不保存：

- API Key / 千问凭据（仍用现有进程内会话）
- CanonicalRecord / 患者行
- 其他 session 的目标
- 模型对质量门的自评

事实仍以 Evidence / 主表 / 质量报告为准。记忆如果与质量门冲突，以质量门为准。

## 6.3 生命周期

| 阶段 | 行为 |
|---|---|
| 创建 | Router 判定进入科研，或用户点“新研究”时创建 session_id |
| 活跃 | Copilot / Planner / Discovery / Integrate 只读写该 session |
| 修订 | 用户新约束以补丁追加，不覆盖审计历史 |
| 过期 | 与现有工作台会话对齐，默认进程内、可设数小时 TTL |
| 结束 | 用户新建研究或主动结束；旧记忆只读归档，不自动带入下一题 |
| 禁止持久化密钥 | 记忆可以落本地任务状态，不得进 git，不得写 `.env` |

第一期记忆可以只在后端进程内存 + 现有 loop store 风格的任务旁路中。不设计成跨用户的长期档案库。

## 6.4 如何避免污染不同研究

1. **硬隔离键：** 所有记忆读写必须带 `session_id`。没有 session 就没有记忆。
2. **新研究切断：** “新建研究”生成新 session，不继承排除来源、失败检索、旧合同。
3. **领域切断：** 同一浏览器若先做乳腺癌再做超新星，必须是两个 session；Copilot 发现 domain 切换时，应询问是否开新研究，默认不开自动合并。
4. **事实不进记忆：** 不把上一题的患者表当作下一题背景知识。
5. **编译隔离：** 肿瘤编译器只读取本 session 的合同 ID，不读取全局“最近一次乳腺癌任务”。
6. **图隔离：** Evidence Graph 按 session/task 建图，查询默认不跨图。

这是审计里“任务隔离、研究隔离、会话隔离”在交互层的延续。

## 6.5 与 ClosedLoop 的关系

现有 ClosedLoop 的输入哈希防空转继续有效。Session Memory 中的 `failed_searches` 可供 Copilot 解释“上一轮为什么没换到 METABRIC”，但第二轮合法补搜仍由旧闭环控制器和 Discovery 执行，不由记忆直接派发工具。

# 7. Figure Understanding Demo

## 7.1 目的

比赛需要看见“系统能看图”，但不能破坏“模型不得随便生成图表数据”的安全原则。V3.1 把图像能力定义成**理解演示**，不是**数字化入库**。

它挂在 Multimodal Extraction Agent 下，作为可开关的展示分支。

## 7.2 输入

- source_id（必须，通常是论文或文件）
- 图位置：页码、figure 编号、PMC 图注或图片标识
- 可选：已有 caption 文本（现有 JATS 图注可复用）

没有 source_id 的图，拒绝理解。

## 7.3 输出（只描述，不进主表）

输出是图理解卡，不是观测表：

| 字段 | 含义 |
|---|---|
| figure_type | 如 light_curve、kaplan_meier、heatmap、western_blot、unknown |
| x_axis | 轴语义假说，如 phase_day、time、gene |
| y_axis | 轴语义假说，如 magnitude、survival、expression |
| legend | 图例文字摘要 |
| extractability | none / caption_only / axes_only / digitization_possible |
| digitization_possible | 是否看起来可数字化 |
| confidence | 0 到 1 |
| status | UNDERSTOOD / REVIEW / FAILED |
| enters_primary_table | 恒为 false（第一阶段） |

示例理解结果：

```text
figure_type: light_curve
x_axis: phase_day
y_axis: magnitude
digitization_possible: true
confidence: 0.87
enters_primary_table: false
```

即使 `digitization_possible=true`，第一阶段也只展示这张卡片，并写入 Evidence Graph 的 `FigureUnderstanding` 节点。

## 7.4 与抽取、融合的边界

```text
JATS 图注        → 现有 parser，可作 caption
Figure Understanding → 图类型 / 轴 / 可提取性
像素数字化        → V3.1 不提供成功路径
主表             → 只接受 Adapter 或表格解析后的带 raw 记录
```

Copilot 可以告诉用户：“这张图像光变曲线，横轴可能是相位，但数字尚未核验，没有写入分析表。”

## 7.5 展示位置

- 规划工作台 / 高级工作台增加“图理解”卡片
- 证据图可查询该节点由哪篇论文、哪条 caption 支撑
- 导出可以附理解卡，但不得出现在主数据 sheet 里冒充观测值

# 9. 最终数据流

## 9.1 Demo 主流程（医学最佳实践）

```text
用户：研究 HER2 阳性乳腺癌耐药机制
  → Router：RESEARCH / oncology
  → Copilot：复述对象与目标，建议临床/表达/突变/药敏，询问机制还是预测
用户：疗效预测；不要 METABRIC；只要公开新辅助
  → Memory：目标=疗效预测；排除=METABRIC；约束=新辅助公开队列
  → Planner：通用合同
  → Schema Generator：绑定冻结 oncology canonical，不新造 HER2 语义
  → Discovery：Registry 医学插件 → GEO / GDC / cBioPortal / 试验 / 文献
  → SourceBroker：组合；METABRIC 因用户排除不进主选
  → ExecutionBridge：ResearchAgentService
  → Quality Gate：IHC 2+、response_domain、身份、Evidence 规则照旧
  → Graph + Copilot 回述：主表来自哪、缺什么、为何 REVIEW
```

## 9.2 通用科研旁路（天文示例）

```text
用户：整理 Ia 型超新星多波段光变公开表
  → Router：RESEARCH / astronomy
  → Copilot：建议观测时间、波段、流量、红移；询问是否只要公开表
  → Planner + Schema Generator：任务级 pack（sn_id, observation_time, band, flux, redshift, 溯源三件套）
  → Discovery：Registry 天文插件 → ADS / Zenodo / Open Supernova Catalog（多为 catalog）
  → Extraction：用户文件或论文表
  → Figure Understanding：识别 light_curve，不入库
  → Matcher 对齐到任务 pack
  → Quality：仅溯源规则
  → 导出 REVIEW 数据包
```

这条流证明系统是通用智能体。它不调用医学规则，也不声称拥有肿瘤 SDTI。

## 9.3 闲聊截止流

```text
用户：你好 / 什么是红移
  → Router：CHAT 或 CONCEPT_QA
  → Copilot：回答或不进入研究
  → 不写研究目标记忆
  → 不生成 schema_pack
  → 不 Discover / Integrate
```

# 10. 开发优先级（P0 到 P5）

原则仍然是增量旁路。每一期结束都必须跑现有医学回归。P0 改为用户能感觉到这是科研助手，而不是先做完所有后台桥。

## P0：Research Copilot + Router + Planner

**目标**

用户输入科研问题后，先看到理解、数据需求建议和必要澄清；确认后再生成合同。闲聊不得进入科研链。肿瘤问题确认后仍能编译到现有 Frozen Contract。

**修改范围**

- 新增 Copilot 与最小 Session Memory（目标 / 澄清回答）
- 调整 Router：科研任务先到 Copilot
- Planner 门面读取 Copilot ready 标记
- 前端规划工作台先展示 Copilot 回复
- 不改 Adapter、Matcher、Quality、Agent 主过程

**风险**

- 澄清过多会像问卷，而不像助手
- 若 ready 条件过松，会回到 V3.0 一提交就开跑
- 若 ready 过严，医学 Demo 会卡住

**验收标准**

- “你好 / 什么是 HER2”不产生合同，不调用 Adapter
- HER2 耐药示例先复述再提问，不直接 integrate
- 用户确认“疗效预测”后，Planner 才能输出肿瘤合同
- 现有肿瘤 API 直连路径仍可用，作为兼容后门
- 旧 pytest 全通过

## P1：Universal Discovery

**目标**

Discovery 通过 Registry 找来源。医学插件指向现有 Adapter；天文/材料可先以 catalog/planned 登记。

**修改范围**

- 新增 Source Registry 配置与查询
- Discovery 改为按 Registry 过滤工具
- Copilot 的“可能需要去哪里找”读取 Registry
- 不新写 NASA/Materials 官方 Adapter
- 不把示范 GSE 写进 Registry 当通用真理

**风险**

- 把 planned 来源展示成已取数
- Registry 与旧种子目录双源不一致

**验收标准**

- 医学任务仍能发现 GEO / GDC / cBioPortal，且 fetch 仍走旧工具
- catalog_only 不能变成字段已覆盖
- 关闭医学插件后，肿瘤自动 INTEGRATE 失败是诚实失败
- 天文任务可以列出 ADS/Zenodo 候选，但不伪造光变主表
- 旧 SourceBroker 测试期望不变

## P2：Dynamic Schema

**目标**

医学高风险字段强制冻结 pack；通用任务可生成任务级 schema_pack，并交给现有 SchemaMatcher 当目标清单。

**修改范围**

- 新增 Schema Generator
- Planner 输出增加 schema_pack_id
- Matcher 调用处增加“目标 pack”参数，不改匹配算法本体
- 不修改 `canonical_schema.yaml`

**风险**

- 通用 pack 误用 patient_id/HER2 字段名
- 生成 pack 被当成新冻结标准
- Matcher 目标切换影响肿瘤回归

**验收标准**

- 乳腺癌患者级任务的 pack 绑定冻结 schema，HER2 规则仍生效
- 超新星示例能生成 sn_id / time / band / flux / redshift + 溯源三件套
- 生成 pack 含 source_id/raw_field/raw_value
- 肿瘤 Matcher 回归与现网一致
- 无澄清完成时不生成完整通用 pack

## P3：Evidence Graph

**目标**

证据图成为 Copilot 回述、前端溯源、质量解释的唯一关系源，并纳入会话约束与图理解节点。

**修改范围**

- 落实 V3.0 图模型
- 增加 CopilotTurn、MemoryConstraint、SchemaPack、FigureUnderstanding 节点
- 前端溯源改为读图查询
- EvidenceBuilder 仍是事实权威

**风险**

- 再做一份展示用假图
- 误加患者跨研究边
- 把记忆约束画成已验证来源

**验收标准**

- 能回答：这个标准值的 raw 是什么、来源如何被发现、为何 REVIEW
- 无 SAME_PATIENT / JOINED_ACROSS_STUDY
- “排除 METABRIC”显示为用户约束边，不是数据缺失证明
- 旧 Evidence 字段不被图覆盖

## P4：Multimodal 与 Figure Understanding

**目标**

统一抽取门面保持 V3.0 安全策略；补上可演示的图理解卡。数字仍不进主表。

**修改范围**

- Extraction 编排包装现有五解析器
- 新增 figures/understand
- 工作台展示图类型、轴、图例、可提取性
- 不提供像素数字化成功 API

**风险**

- 评委把理解卡误认为已提取光变数据
- 模型补全轴上的数值

**验收标准**

- `test_parsers.py` 期望不变
- 无文本层 PDF 仍 REVIEW
- 图理解结果 `enters_primary_table=false`
- 界面与导出都标明“理解演示，非主表数据”
- 不存在数字化入库路径

## P5：高级能力

**目标**

只在前四期稳定后考虑：PDF 版面表 REVIEW 候选、通用来源的第一个真实 Adapter、受控的图像数字化人工确认、跨会话只读档案。均为可选项。

**修改范围**

- 独立开关，默认关闭
- 每个新 Adapter 单独立项和测试
- 任何数字化进入分析表必须人工确认

**风险**

- 过早追求“更像 ChatGPT”而松开质量门
- 把 P5 写成已经具备的通用平台能力

**验收标准**

- 默认关闭时，系统行为与 P4 完成态一致
- 未实现能力返回明确未实现，不填分数
- 医学 SDTI 公式与 Gold Set 口径仍不改
- 不宣布新的正式 SDTI

# 11. 最终 Demo 流程

面向评委或用户的一条完整故事，应能在不改内核的前提下讲清楚“通用智能体 + 医学插件”。

## 11.1 开场定位

系统先显示自己是通用科研数据智能体。医学是已经装好的高质量插件。

## 11.2 场景一：连续科研对话（必须有）

1. 用户输入 HER2 阳性乳腺癌耐药。
2. Copilot 复述对象与目标，列出数据需求，只问一个关键问题。

4. 用户第二轮排除 METABRIC，要求公开新辅助队列。
5. 用户第三轮加入 PIK3CA。

1. Planner 冻结合同，Schema 绑定冻结医学 pack。
2. Registry 显示本次启用的医学来源插件。
3. 旧执行引擎取数、对齐、过质量门。

5. 若有论文图，展示 Figure Understanding 卡片，并写明未写入主表。

## 11.5 场景四：拒绝胡说（信任）

1. 闲聊不进流程。
2. 细胞系 AUC 不能当作患者 pCR。
3. 图上的数字不能进主表。
4. 质量门 REVIEW 不会被 Copilot 说成已经完成。

# 12. 终稿收束

V3.1 在 V3.0 上增加的是感知层、注册层、任务契约层、记忆层和图理解展示层。它让系统更接近 ChatGPT 类科研 Agent 的**交互与连续规划**，同时把 ChatGPT 最危险的部分继续留给可信工厂：

- 事实仍来自 Adapter 与解析器
- 医学语义仍来自冻结 schema 与规则
- 发布权仍在 Quality Gate
- 记忆不能污染另一项研究
- 图像先理解，后才谈不谈数字化

因此，升级后的系统定位不再是“医学数据系统”，而是：

**通用科研数据发现与可信整合智能体，医学是第一个高质量领域插件。**

本文只做架构终稿，不修改代码。
