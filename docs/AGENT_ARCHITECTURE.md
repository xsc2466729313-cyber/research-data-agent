# Agent 系统架构说明

## 一句话定义

本系统是**有边界的混合式多 Agent 编排系统（bounded hybrid multi-agent orchestration）**：由一个任务级主 Agent 统一推进任务，由多个职责隔离的专用 Agent/控制器处理问题解析、研究规划、缺口补搜、独立审查和闭环修正；公开数据 Adapter、字段标准化、医学规则和最终质量门仍是独立的确定性模块。

因此，系统既不是“一个大模型 Prompt 包办所有工作”的单 Agent，也不是没有总控、没有共享契约的完全去中心化 Agent 集群。

## 运行时角色与边界

| 角色 | 运行时组件 | 负责什么 | 明确不负责什么 |
|---|---|---|---|
| 任务级主 Agent | `ResearchAgentService` | 接收任务、调用模型规划、编排工具、汇总结果、生成科研数据包 | 不直接把模型文本当患者事实，不绕过质量门 |
| 问题/研究规划 Agent | Qwen `extract_research_spec`、`choose_tools`；`ResearchIntentAgent`、`ResearchFormulationAgent` | 把自然语言拆成研究对象、暴露、结局、字段和候选来源 | 不下载数据、不修改原始记录、不做医学发布裁决 |
| 采集与缺口 Agent | `CollectionAgent` + `GoalLoopController` | 观察字段缺口，诊断缺口原因，选择尚未尝试的检索方法和停止条件 | 不用其他患者或知识证据填补主表，不跨研究强行合并 |
| 工具/数据 Adapter 层 | GDC、GEO、cBioPortal、AACT、CIViC、DepMap 等 Adapter | 访问官方来源、解析原始返回、登记 `source_id`、URL 和原始字段 | 不理解用户意图，不生成不存在的患者事实 |
| 证据与对齐模块 | `ResearchDatasetBuilder`、Schema/Entity Matcher、`DataAlignmentAuditor` | 标准化字段、构造患者/样本级表、保留 `raw_field/raw_value` 和来源边界 | 不把低置信度关联自动变成确定身份 |
| 独立批评 Agent | `CriticAgent` | 对 Research Contract、字段覆盖、结局域和来源完整度提出诊断 | 不直接改写数据；高风险问题只进入 review |
| 质量 Agent / 规则门 | `QualityAgent`、`QualityV2Service`、`medical_rules.yaml`、`RulePackEngine` | 独立检查缺失、冲突、医学禁用语义和发布准入 | 不接受模型自证，不自动修复高风险事实 |
| 闭环控制器 | `ClosedLoopService` | 保存轮次状态，依据质量反馈生成下一轮输入，防止重复调用和空转 | 不改变事实字段，不代替 Critic 或 Quality Gate |

规划子 Agent（意图、问题构造、字段规划、指标规划）是可测试的专用组件；它们在同一个任务边界内协作，不共享无关历史。`ClosedLoopService` 是控制器，不把它冒充成另一个“会自由发挥的模型 Agent”。

## 上下文隔离

系统通过以下边界隔离上下文，避免一个角色的猜测污染另一个角色的事实：

1. **任务隔离**：每次任务有独立 `task_id`；闭环每轮有独立输入/输出和哈希，状态按任务保存。
2. **研究隔离**：每个 `study_id`、`patient_id`、`sample_id` 和来源命名空间独立保存。不同研究的同名患者编号不构成 Join 条件。
3. **证据隔离**：模型看到的是来源摘要和工具结果；患者/样本事实只能从 Adapter 返回进入数据集，必须带 `source_id`、`raw_field`、`raw_value`。
4. **职责隔离**：规划 Agent 只能提出计划，Adapter 只能取数，Critic 只能诊断，Quality Gate 只能裁决；任何单个角色都没有“全链路写权限”。
5. **会话隔离**：千问会话凭据和短期上下文只保存在临时内存，不写入仓库；过期会话不能继续执行生产任务。

## 关注点分离

系统把“生成”和“事实”拆开：

```text
自然语言问题
  → 规划 Agent：提出 ResearchSpec / 工具计划
  → 官方 Adapter：取得真实来源和原始记录
  → 确定性整合：Schema、实体、response_domain、来源登记
  → Critic：独立诊断合同缺口和语义冲突
  → Quality Gate：按冻结医学规则决定 PASS / REVIEW / FAIL
  → 闭环控制器：只针对缺口选择下一轮合法动作
```

这条边界保证模型可以“建议”，但不能单独“证明”；数据可以“被整理”，但不能在缺少 Evidence 时“被发布”。

## 并行策略：能并行，但不是所有步骤都并行

### 可以并行的场景

- 同一轮内彼此独立的只读来源查询，例如 GDC、GEO、cBioPortal 的独立入口。
- 只依赖同一个 `ResearchSpec`、不互相写状态的候选检索、来源健康检查和文献发现。
- Qwen Function Calling 已通过 `parallel_tool_calls=true` 表达同轮独立工具调用意图。

### 必须串行或汇合后再做的场景

- 需要根据上一轮结果决定下一轮动作的闭环补搜。
- 共享同一个主数据集、实体索引或去重状态的写操作。
- Schema/Entity 对齐、跨来源候选排序、Critic 和 Quality Gate，因为它们必须看到完整的汇总结果。
- 任何可能触发医学安全规则或发布状态改变的操作。

当前生产主链对工具结果采用**受控串行执行 + 统一汇总**，优先保证来源登记、顺序可复现和审计稳定；规划层仍支持把独立调用标记为可并行。未来若启用并发执行，必须使用只读任务隔离、幂等写入和汇合点校验，不能为了缩短延迟牺牲可追溯性。

## 独立校验链

系统至少保留三道相互独立的检查：

1. **Adapter/Schema 校验**：响应结构、字段类型、来源编号和原始值是否存在。
2. **Critic 校验**：研究合同、目标字段、结局域、来源证据是否足够回答问题。
3. **Quality/Medical Gate**：缺失 Evidence、HER2 IHC 2+、ERBB2 CNA 与 HER2 IHC 混淆、低置信度身份关联、细胞系药敏与患者结局混用等风险是否阻断发布。

模型输出即使格式正确，也必须经过后两道检查；校验模块不读取模型“自评为正确”的结论作为证据。

## 为什么不是“单 Agent + 多职能 Prompt”

把所有职责塞进一个 Agent 看似简单，但在本任务中会产生结构性问题：

- **上下文污染**：规划时的假设容易被带入患者事实和最终摘要。
- **权限混杂**：同一个角色既能选择来源又能修改字段并宣布通过，无法形成真正的制衡。
- **无法独立质疑**：模型自己生成、自己解释、自己验收，错误会以流畅文本通过。
- **失败隔离差**：一个数据库超时、解析异常或错误重试可能污染整条上下文，难以只重跑单个职责。
- **并行与审计困难**：所有工具、规则和写操作共享同一个状态，无法安全区分可并行读操作与必须串行的汇合步骤。
- **评测不可归因**：无法回答是问题解析、检索、字段对齐还是质量门导致结果变化。

当前架构让每个职责都有输入/输出契约、版本和可测试边界，所以能够独立替换、独立回归和独立解释。

## 哪些场景反而不该上多 Agent

多 Agent 不是默认答案。以下场景应优先使用单一确定性函数或简单流水线：

- 单来源、单字段、只读查询，例如按已知 GSE accession 查询元数据。
- 纯格式转换、去重、大小写归一化、允许列表别名替换等确定性操作。
- 有明确事务边界的写入、删除或状态更新；多角色并发会增加锁和一致性风险。
- 低延迟、低成本、输入规模很小且没有跨步骤推理的请求。
- 需要严格复现的离线评测基线；应关闭模型和多 Agent 自主规划，使用固定脚本。

本系统因此采用“**复杂研究任务多 Agent，局部确定性任务单模块**”的策略：只有在存在多来源选择、证据边界、缺口反馈或独立质量裁决时，才引入 Agent 编排。

## 可评分结论

- 架构类型：有总控、有契约、有独立审查的混合式多 Agent。
- 上下文隔离：按任务、研究、来源、职责和会话五层隔离。
- 关注点分离：规划、取数、整合、批评、质量门和闭环控制分别负责。
- 并行能力：独立只读来源可并行表达/执行；共享状态、闭环和医学裁决必须串行。
- 独立校验：Critic 与 Quality/Medical Gate 不接受模型自证。
- 使用边界：简单确定性任务不强行多 Agent，避免额外延迟、成本和一致性风险。
