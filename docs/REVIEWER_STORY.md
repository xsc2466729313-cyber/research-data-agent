# 评委讲故事闭环版：从研究问题到可信数据交付

## 先用一句话讲清楚

科研人员提出的不是“请模型讲一段知识”，而是一个需要多来源、患者级、可核对数据才能回答的问题。本系统用一个主 Agent 负责统筹，用多个专业 Agent 分别规划、检索、质疑和把关，再用固定规则模块守住真实数据、字段含义、身份对应和医学安全，最后只交付有来源、可复核的数据包。

## 第一幕：我们要解决什么问题

多癌种精准治疗研究通常同时需要目标人群、分子变异、治疗方案和疗效记录。这些信息分散在论文、患者队列、基因组数据库和临床试验登记中：

- 同一个概念可能有不同字段名，不能只按列名拼接。
- 同一个患者编号只在所属研究中有效，不能因为编号相同就跨研究合并。
- HER2 检测结果、ERBB2 拷贝数变化和细胞系药敏不是同一种医学事实，不能混成一个结论。
- 找不到关键证据时，系统必须明确说“缺口待补查”，不能用模型生成内容填空。

所以真正的问题是：**如何把一句自然语言研究问题，变成一份真实、可追溯、知道边界的数据交付包。**

## 第二幕：我们怎样设计 Agent 关系

本系统是“有边界的混合式多 Agent”，不是一个大 Prompt 包办所有事情，也不是没有总控的 Agent 集群。

### 关系用大白话说明

1. **主 Agent｜任务总控**接收研究问题，拆成可执行任务，安排下一步并管理任务上下文。
2. **规划 Agent**接收任务顺序，把问题写成研究对象、变量、结局、字段和来源计划。
3. **检索 Agent**接收研究方案和字段清单，分别查找患者资料、论文证据和试验信息；互不依赖的查找可以并行。
4. **固定规则模块｜数据整理**接收真实来源和原始记录，统一字段、保留原字段与原值、登记来源，并按研究边界保存患者和样本关系。
5. **Critic Agent**接收标准数据和证据，只负责找缺口、冲突和身份问题，不直接修改事实。
6. **Quality Agent**接收问题清单和质量指标，结合冻结医学规则决定通过、人工复核或阻断。
7. **闭环控制器**把未解决的缺口变成下一轮合法检索任务；资料不足就补查，发现冲突就回到检索，不让系统凭空补写。

关系可以压缩成一句话：

```text
研究问题
  → 主 Agent 统筹
  → 规划 Agent 明确需要什么
  → 检索 Agent 找真实来源
  → 规则模块整理并登记来源
  → Critic Agent 独立找问题
  → Quality Agent 判断能否交付
  → 数据交付 / 补查 / 人工复核
```

### 为什么不能只用一个 Agent

一个角色同时“想方案、找资料、改数据、自己检查、自己宣布通过”，会出现四个结构性问题：规划中的猜测容易污染患者事实；取数和发布权限混在一起；模型无法真正质疑自己的结论；出现错误时也无法判断是解析、检索、对齐还是质量门出了问题。

因此本系统采用职责隔离：规划只能提出计划，Adapter 只能取得真实记录，规则模块只能按固定程序整理，Critic 只能诊断，Quality 只能裁决。没有任何一个角色拥有全链路写入和发布权限。

### 上下文隔离、关注点分离、并行和独立校验

- **上下文隔离**：按 `task_id`、闭环轮次、`study_id/patient_id/sample_id` 和来源命名空间保存状态；不同研究的同名患者编号不会自动 Join。
- **关注点分离**：规划、取数、整理、批评、质量裁决和闭环控制各有输入输出，模型建议与患者事实分开保存。
- **可以并行**：同一轮中互不依赖的患者资料、论文证据、试验信息和来源健康检查可以并行；共享数据集写入、身份合并、质量裁决必须汇合后串行。
- **独立校验**：Adapter/Schema 先检查结构和来源，Critic 再检查研究条件与证据，Quality/Medical Gate 最后检查医学禁用语义和发布准入；模型不能用自己的摘要自证正确。

### 哪些场景反而不该用多 Agent

已知编号的单来源查询、格式转换、确定性去重、大小写统一、允许列表替换和严格复现的离线基线，使用单一确定性函数更快、更省资源，也更容易复现。多 Agent 只用于存在多来源选择、证据缺口、跨步骤反馈或独立质量裁决的复杂研究任务。

## 第三幕：设计之后，系统实际产出了什么

乳腺癌代表任务把“研究 HER2 阳性乳腺癌中 PIK3CA 突变与术前治疗效果的关系”落实为可检查的数据需求。系统完成 **2 轮采集、6/6 次真实工具调用、50 条来源记录**，形成 **1 张主数据表和 3 张补充数据表**；主数据表为 **115 行 × 31 列、42 名患者**。GSE76360 补充表得到 **50 名治疗前已有记录的 HER2 阳性患者**，其中 **48 条疗效记录**可以用于患者组内的疗效构成描述。

系统没有把不同研究中的患者强行拼接。当前仍缺少“同一 HER2 阳性新辅助治疗患者组中的患者级 PIK3CA 分子资料”，因此输出下一步是同队列附件补查或新队列检索，而不是生成一个看似完整的医学结论。

## 第四幕：指标说明了哪些能力

### 公开能力对照

| 能力 | 本项目结果 | 对照结果 | 说明了什么 | 解决了什么问题 |
|---|---:|---:|---|---|
| 问题解析 F1 | **0.5522** | 词典 0.4662 | 比旧方法 **+0.0860**，更能找准研究对象、治疗和结局边界 | 减少把治疗方案、治疗阶段和疗效混为一谈 |
| 科学检索 nDCG@10 | **0.3915** | BGE 0.3880 | **+0.0035**；前十命中率和前百召回率也同步提升 | 让相关材料更早出现，同时扩大候选覆盖 |
| 字段匹配 F1 | **0.9018** | 项目原方法 0.7994 | **+0.1024**，对缩写和语义改名更有效 | 减少不同数据库列名不同造成的漏配 |
| 实体匹配 F1 | **0.7449** | RecordLinkage 0.7440 | 基本持平，只能生成候选 | 说明患者关联仍必须依靠研究编号、来源和人工复核 |
| 错误清洗 F1 | **0.9169** | Raha 0.8159 | 六项本项目结果；五项共同任务 **0.9029 对 0.8159** | 对有重复来源依据的错误进行可验证修复 |

这些分数不是一个笼统的“模型准确率”。每个分数只回答一段能力：问题解析回答“理解对不对”，检索回答“材料找得准不准”，字段匹配回答“列名能否对齐”，实体匹配回答“能否提出关联候选”，清洗回答“错误能否被证据支持地修复”。

### 完整链路与安全指标

严格千问在线全链路在 11 个问题上实际调用千问 11 次、确定性兜底 0 次，得到 **15 个正确来源、0 个错误来源、3 个遗漏**：

- Retrieval Precision = **100.00%**：没有用无关来源换取覆盖。
- Retrieval Recall = **83.33%**：仍有 3 个目标来源遗漏，补查机制仍有价值。
- Retrieval F1 = **90.91%**：达到冻结目标 0.90。
- Faithfulness = **100.00%（26/26）**：抽检关键字段均保持原始医学语义。
- Traceability = **100.00%（26/26）**：关键非空字段均有完整 Evidence。
- Error F1 = **100.00%（15/15）**：发现的错误全部有依据。
- Repair Accuracy = **100.00%（3/3）**：3 次自动修复全部正确。
- SDTI = **98.1118**：五项指标的几何平均，反映整条数据链的短板效应。
- Fake source rate = **0/251 = 0%**：没有发现虚假来源。

这些指标合起来说明：系统已经具备“理解问题、找到来源、保留原义、逐项回查、发现错误、正确修复”的能力。但当前题集参与过开发，8 个实时任务仍有质量门 REVIEW，尚未完成 sealed frozen_test，因此 `publish_allowed=false`。**98.1118 是工程复测成绩，不是可以绕过安全门的发布许可。**

## 第五幕：能力如何形成价值闭环

```text
研究问题复杂、来源分散、身份容易混淆
  ↓
多 Agent 分工 + 固定规则守边界
  ↓
问题解析、检索、字段对齐、清洗和质量门分别变好
  ↓
数据有来源、字段保留原义、问题可定位、错误可复核
  ↓
研究者不必在多个网站和表格之间反复猜测
  ↓
能够更快形成可分析、可复用、可继续补查的科研数据包
```

换成评委听得懂的因果链就是：

1. **问题**：研究者需要把人群、基因、治疗和疗效放在同一个研究问题里，但资料分散且口径不一。
2. **设计**：让主 Agent 统筹，让专业 Agent 分工，让固定规则守住事实和医学边界。
3. **指标**：问题解析提升 0.0860，字段匹配提升 0.1024，清洗五项共同任务提升 0.0870；完整链路 SDTI 为 98.1118，关键字段忠实度和可追溯率均为 100%。
4. **能力**：系统能把自然语言变成字段需求，找到真实来源，统一表达，同时知道哪些记录不能安全关联。
5. **直接解决的问题**：减少漏找、错配、无来源发布和跨研究误合并；缺口会变成下一轮补查，而不是被模型编造填平。
6. **研究意义**：研究者拿到的是能回查、能复核、能继续扩展的数据基础，后续统计和建模的分母、字段和来源都有依据。

## 第六幕：三分钟汇报讲稿

> 我们面对的问题不是模型会不会回答，而是科研人员能不能拿到一份真正可用的数据。精准治疗研究同时需要患者、基因、治疗和疗效，但这些信息分散在论文和多个数据库里，字段写法不同，患者编号也只在所属研究中有效。只把搜索结果拼在一起，会得到一张看起来完整、实际上无法核对的表。
>
> 因此我们没有让一个 Agent 包办全部工作，而是设计了一个有边界的混合式多 Agent。主 Agent 负责统筹，规划 Agent 明确需要什么，检索 Agent 查找患者资料、论文证据和试验信息，固定规则模块负责真实取数、字段整理和来源登记，Critic Agent 专门找缺口和冲突，Quality Agent 最后按医学安全规则决定能否交付。模型可以提出下一步，但不能把猜测写成患者事实。
>
> 这套分工不是为了增加角色，而是为了形成制衡。上下文按任务、研究和来源隔离；独立资料查找可以并行，共享写入和医学裁决必须串行；Adapter、Critic 和 Quality Gate 分别检查结构、证据和安全，模型不能自己生成、自己解释、自己验收。
>
> 在乳腺癌代表任务中，系统完成 2 轮、6 次真实工具调用，登记 50 条来源记录，形成 1 张主表和 3 张补充表。它得到 50 名 GSE76360 治疗前已有记录的 HER2 阳性患者，其中 48 条疗效记录可核对；但它没有因为主题相近就把其他研究的 PIK3CA 数据硬拼进来，而是明确输出下一步缺口。这说明系统交付的是可核对的数据基础，不是假装完整的医学结论。
>
> 指标也要放回能力看。问题解析 F1 从 0.4662 提升到 0.5522，说明研究条件拆得更清楚；字段匹配 F1 达到 0.9018，说明不同数据库的列名更容易对齐；错误清洗六项平均为 0.9169，说明有来源依据的错误可以被发现和修复。严格千问在线全链路的精确率是 100%，召回率是 83.33%，检索 F1 是 90.91%，关键字段忠实度和可追溯率都是 100%，SDTI 是 98.1118。它证明系统能找、能理、能查、能修，但也诚实保留 3 个遗漏和 REVIEW 状态。
>
> 所以我们的价值不是让模型替研究者下结论，而是把“为什么找这些数据、实际拿到了什么、哪些记录能安全关联、哪里还缺证据、能不能交付”固定成一条可检查、可修正、可继续推进的科研数据链。

## 最后回答评委可能追问的问题

**问：这是单 Agent 还是多 Agent？**\r\n答：是有主 Agent 的混合式多 Agent。主 Agent 统一推进，规划、检索、质疑和质量把关由不同专业角色完成；真实取数、字段整理、身份核对和医学规则属于确定性模块。

**问：为什么不做一个 Agent 加多职能 Prompt？**\r\n答：那样会把规划假设、患者事实和最终发布混在同一上下文里，权限也混在一起，无法真正独立质疑，错误还无法归因。当前每个角色都有边界和输入输出契约。

**问：多 Agent 是否全部并行？**\r\n答：不是。互不依赖的只读资料查找可以并行；共享写入、身份合并、闭环补查和医学裁决必须串行汇合，优先保证审计可复现。

**问：实体匹配只有 0.7449，为什么还说系统可靠？**\r\n答：这个指标只说明通用实体匹配可以生成候选，不能证明患者身份。系统正因为承认这个短板，才要求研究编号、患者/样本编号和来源证据共同确认，低置信度进入 REVIEW。

**问：哪些场景不该用多 Agent？**\r\n答：单来源查询、格式转换、确定性去重、大小写统一和严格离线基线不需要多 Agent；多 Agent 只用于多来源选择、证据缺口、反馈闭环和独立质量裁决。

**问：SDTI 98.1118 是否等于可以自动发布？**\r\n答：不等于。SDTI 是五项技术指标的几何平均；安全门还要检查虚假来源、高风险未解决问题和封存题集状态。本轮仍为 REVIEW，`publish_allowed=false`。

**问：系统最终解决了什么？**\r\n答：把分散的检索、取数、字段治理、身份核对和质量审查连接成一条可追溯数据链，让研究者拿到的不只是答案，而是能继续分析、复核和补查的数据基础。
